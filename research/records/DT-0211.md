# DT-0211 — Migrate high-resolution tile metadata to `location.csv`

- **Branch:** `feature/package-builder`
- **Starting commit:** `8258ec28f84dde12da71f68e37e66d9065dc7579`
- **Status:** Implemented; focused tests and format checks passed. One preserved legacy Fortran reference test fails under the current GNU Fortran runtime. Changes remain uncommitted.

## Objective and design constraint

Make `location.csv` the standard high-resolution tile inventory for maintained v5 NetCDF workflows. Follow the maintainer decision in [DR-0064](discussions/DR-0064.md): do not distribute legacy parsing through ordinary v5 workflows, do not build the future conversion tools in this task, and retain TXT only where an active Binary or unmigrated-map workflow still needs it.

## Implementation

Added shared CSV inventory parsing/writing and validation in `map/tools/code/hires_metadata.py`. The schema is ordered as `iarea,carea,west,east,south,north,nx,ny,csize`; each row is one listed tile, aligned CSV padding is stripped, and missing tiles are not inferred. NetCDF preprocessing, allocation, parameter, CTL, high-resolution conversion, Map Explorer, and river-map consumers now use the standard CSV inventory. NetCDF-producing regional workflows write CSV. Shell selectors and `s09-write_ctl.sh`, documentation, the map metadata specification, and the registry now describe the standard format.

The shared helper also reads/writes TXT for explicit conversion and Binary compatibility paths. Existing Binary converters continue producing or consuming Binary-side TXT. Map Explorer continues to recognize a TXT-only map so currently installed external maps remain usable; the shared conversion selector recognizes legacy descriptors only at the format-conversion boundary. These are temporary compatibility paths, not a new general-purpose fallback policy. Historical Fortran sources were left intact.

## On-disk map migration

Searched the filesystem under `map/`, including ignored datasets. Seven existing `location.txt` files were found. A colocated CSV was generated for each and parsed back to confirm exact equality of all nine fields for every row. All seven original TXT files remain. The two Mekong CSV inventories are untracked sample metadata additions; five CSV inventories for ignored Global, Rhine, and TE-Japan data remain ignored. No raster or unrelated data file changed.

## Validation

See [VR-0256](validation_runs/VR-0256.md). The focused map-tool suite passed 87 tests and 31 subtests; the Map Explorer native-NetCDF inventory suite passed 14 tests. All seven local CSV/TXT pairs matched exactly. Python syntax compilation, modified Shell syntax checks, the map variable registry validator, and `git diff --check` passed. One legacy Fortran-reference parity case was excluded from the passing suite because its direct-access read fails under the available compiler with `Record number not allowed for sequential access data transfer`; the Fortran source was not changed. These checks establish interface and fixture behavior for the tested cases, not universal scientific correctness.

## Remaining compatibility work

1. `map/tools/code/hires_metadata.py` retains the counted TXT reader/writer used by explicit Binary conversions.
2. Binary-specific branches in `mod_allocation_map_io.py`, `param_water_calc_prmwat.py`, `analysis_river_point_info.py`, `region_combine_hires.py`, `generate_ctl.py`, and `mod_map_io.py` retain TXT handling for explicitly selected legacy Binary maps or Binary path resolution.
3. `convert_highres_binary_to_netcdf.py`, `convert_highres_netcdf_to_binary.py`, and `tools/shell_functions/cmf_select_hires_for_conversion.sh` retain TXT support at the explicit conversion boundary.
4. `visualization/map_explorer/code/hires.py` retains discovery of TXT-only external maps that have not been migrated.
5. `map/tools/code/legacy_fortran/` and map-local legacy Binary scripts continue to use `location.txt`; they were not rewritten.

After the dedicated bidirectional metadata conversion tools are available and active external/Binary workflows are migrated, these compatibility paths can be reviewed and reduced centrally.
