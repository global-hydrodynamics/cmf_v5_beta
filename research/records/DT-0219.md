## Prior constraint and decision

The supplied historical handoff reported that Python 3.8 cannot import
`importlib.resources.files`. Cloud Codex had already reproduced the failure in
its isolated 2020 Linux profile and verified a source-path workaround using
`importlib-resources==4.1.1`. The maintainer requested that this local follow-up
adopt only the small source change and document the Cloud evidence; the Docker
experiments were not repeated.

## Change and evidence

`cmf_colormap.core` now imports `files` from the standard library first and
uses `importlib_resources` only if that API is unavailable. The palette data,
resource consumers, algorithms, colors, and package metadata were left
unchanged. No backport was installed in the current or 2024 environments.

The repository `.venv` and the existing isolated 2024 CPython 3.12 environment
both passed `pip check`, imported the working source, loaded all six palette
registrations, and passed all 25 existing CMF Colormaps tests. This confirms
the normal standard-library branch on the current runtime. It is not a local
Python 3.8 test; that branch evidence remains the completed Cloud experiment
summarized in the [compatibility handoff](../../docs/python_legacy_compatibility_handoff.md).

## Compatibility and scientific impact

- **Scientific method/data change:** No.
- **Package API or support metadata change:** No. `pyproject.toml` remains
  Python >=3.9 and Matplotlib >=3.7.
- **β02 support:** The 2024 profile remains the oldest official fallback.
  Python 2022 and 2020 remain experimental manual probes.
- **Existing user work:** The local `s02-python_setup.sh` and
  `s03-activate_cmf_pyenv.sh` activation work was preserved and verified
  unchanged by SHA-256.

Checklist completed. No material new scientific or architectural gap was
