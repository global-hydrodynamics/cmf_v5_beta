## Trigger, diagnosis and decision

Maintainer reports an extracted β05b01 package failing during rasterio installation with CPython 3.12 arm64: pip selects source and cannot find gdal-config. Their exact macOS version and complete pip log were not supplied. Do not assume their machine's OS from the local reproduction.

The existing shared requirement `rasterio>=1.4,<1.5` admits source archives. On the local macOS 13.7.8 arm64 / CPython 3.12.3, the original pip selection was reproduced in a temporary venv with PATH restricted to /usr/bin:/bin. A dry-run metadata build chose the newer source release and failed with missing gdal-config/GDAL API version. Upgrading pip does not supply missing compatible wheels.

PyPI's official file metadata shows 1.4.1 cp310/cp311/cp312 arm64 macOS 11+ wheels, while 1.4.2/1.4.3/1.4.4 arm64 wheels target macOS 14+. Source references:

- https://pypi.org/project/rasterio/1.4.1/#files
- https://pypi.org/project/rasterio/1.4.3/#files
- https://pypi.org/project/rasterio/1.4.4/#files
- https://rasterio.readthedocs.io/en/stable/installation.html
- https://pip.pypa.io/en/stable/cli/pip_install/
- https://pip.pypa.io/en/stable/topics/configuration/

Wheel-only installation selects 1.4.1 here, but the first real import check exposed another installation compatibility issue: netCDF4 1.6.5 (the available older-macOS arm64 wheel) failed with NumPy 2.5.5, reporting numpy.dtype size changed. NumPy 1.26.4 restores imports and actual Mekong NetCDF reads. This is environment dependency compatibility, not a scientific-reader patch.

## Implementation and protection of existing environments

The macOS pip command additionally uses --only-binary=:all: and --no-user, without globally pinning rasterio 1.4.1 or upgrading pip.

The automatic setup envelope is CPython 3.10–3.12 on macOS 11–13, CPython 3.10–3.13 on macOS 14+, arm64/x86_64. Unsupported setup prints runtime/OS/architecture and guidance before creating a venv. pip is the authority on whether the entire dependency graph has wheels; missing wheels/network/TLS/disk failures stop without source fallback. Supported interpreter discovery includes python.org Framework and optional Homebrew/versioned /usr/local paths. Explicit PYTHON/active/local precedence remains.

Only child-process environment variables are sanitized: pip config is disabled with PIP_CONFIG_FILE=/dev/null, inherited PIP_* and Python path redirections are removed, and VIRTUAL_ENV points to Explorer-local .venv. Parent shell/config files are not rewritten; default PyPI is used. Symlinked venv and prefix mismatches remain refused. Native import failures on macOS offer the same repair flow. Ready environments are not automatically upgraded. No dependency was installed into the existing repository or Explorer environments; actual installs below use disposable directories only.
