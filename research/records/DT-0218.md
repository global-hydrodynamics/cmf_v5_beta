## Scope and behavior

The repository-local environment remains `.venv`, with activation prompt `(cmf50)`. `s02-python_setup.sh` remains responsible for interpreter selection, creation, dependency installation/fallback, and validation. It no longer prints direct activation instructions or manages shell startup files; success points users to `./s03-activate_cmf_pyenv.sh`.

New and clean-fallback environments are created with `--prompt cmf50`. When reusing an existing `.venv`, setup regenerates only the standard activation scripts and changes the `prompt` entry in `pyvenv.cfg`. It does not invoke pip for the prompt change, and it leaves the other venv configuration entries intact.

The new root-level `s03-activate_cmf_pyenv.sh` resolves the repository from its own location, checks `.venv/bin/activate`, detects the user's login shell, and registers `cmfpy` in `~/.zshrc`, macOS Bash's first existing login file (`~/.bash_profile`, `~/.bash_login`, or `~/.profile`), or other Bash `~/.bashrc`. It uses an identifiable managed block, updates an older managed target, is idempotent, and leaves an unrelated alias untouched with a manual activation command. Configuration edits use a temporary file and atomic replacement.

## Documentation and validation

The root README and `docs/python_environment.md` now describe setup, alias registration, reloading the shell configuration, `cmfpy`, and `deactivate`. The focused checks and their boundaries are recorded in [VR-0264](validation_runs/VR-0264.md). Tests used temporary HOME directories and temporary virtual environments; the developer's real shell configuration and repository `.venv` were not changed.

## Knowledge-gap review

No scientific or numerical question was introduced. Shell startup configurations vary across user systems; the helper supports Bash and Zsh and reports unsupported login shells with a direct activation command. Platform-specific shell startup behavior beyond the tested macOS host remains unverified.
